## 1. 에이전트가 하는 일

에이전트는 **질문을 받아 엔진 계산 순서를 정하고, 결과를 검증해서, 화면에 그릴 결과(화면 조각)로 바꾸는 중간 층**이다.
숫자는 직접 만들지 않는다. 계산은 분석 엔진이 하고, 에이전트는 엔진 결과의 `evidence`·`params` 값만 인용한다.

| 층 | 담당 | 하는 일 |
|---|---|---|
| 분석 엔진 (`engine/`) | 현준 | 후보 찾기·유형 분류·배치·강건성 등 계산 |
| **에이전트 (`agent/`)** | 혜진 | 질문 해석 → 도구 호출 → 결과 요약 → 답변 검증 → 화면 조각 생성 |
| 백엔드 | 채원 | 에이전트 호출, 결과 저장, 함께 가기·이동 도움 요청 처리 |
| 프론트 | 사랑 | 화면 조각을 카드·지도·차트·문서 화면으로 그림 |

LLM은 Claude Sonnet 5.5(`claude-sonnet-5-5`)이다. 사용자는 질문창에 묻고, 프론트가 그린 화면으로 답을 받는다.

### 처리할 수 있는 질문

| 모드 | 질문 예 | 에이전트가 쓰는 도구 | 화면 결과 | 예시 |
|---|---|---|---|---|
| 관리자 | 춘천에서 어디부터 확인해야 해? | 후보 찾기 → 유형 분류 → 강건성 + 지역 맥락 | 결론·설명 + 유형 지도 | `5_관리자/01`, `02` |
| 관리자 | 춘천 외곽에 이동형 상담 2곳, 어디가 좋아? | 후보 찾기 → 배치 → 지역 맥락 | 거점 지도 | `03` |
| 관리자 | 지내2리 경로당이 문을 닫으면? | 시설 찾기 → 시설 변화 가정 | 시설 지도 | `04` |
| 관리자 | 이 결과 믿어도 돼? | 강건성 → 현장 확인 목록 | 확인 목록 지도 | `05` |
| 관리자 | 현장 확인 목록 만들어 줘 | 현장 확인 목록 | 확인 수준·질문·방문 순서 | `06` |
| 관리자 | 이동형이랑 경로당 거점 중 뭐가 나아? | 개입안 비교 + 지역 맥락 | 비교 차트 + 거점 지도 | `07`, `08` |
| 관리자 | 사업 제안서 / 현황 보고 / 주민 안내문 써줘 | 필요한 도구 조합 | 문서 (Markdown) | `09`~`11` |
| 시민 | 어머니 댁 근처에 다니실 만한 곳 있어요? | 자원 조회 → 시간대 | 시설 지도 | `6_시민/01`, `02`, `05` |
| 공통 | 안녕 / 오늘 날씨 어때? / 부산은 어때? | 없음 (짧은 답) | 짧은 안내 문장 | `5_관리자/12`~`14` |

표에 없는 질문도 Sonnet 이 필요한 도구를 골라 답한다. 분석이 필요 없는 질문(인사, 관계없는 질문, 서비스 지역 밖, 데이터가 없는 질문)은 짧은 답으로 처리한다.

## 2. 실행

저장소 루트에서 실행한다.

```bash
pip install -r engine/requirements.txt -r agent/requirements.txt
# agent/.env 에 한 줄: ANTHROPIC_API_KEY=sk-ant-...   (git 무시 대상)

python -m agent.run "춘천에서 어디부터 확인해야 해?"                                     # 관리자
python -m agent.run "근처에 갈 만한 곳 있어요?" --mode citizen --lat 37.8813 --lon 127.7298   # 시민
python -m pytest agent/tests -q                                                          # 테스트 (API 키 없이 동작)
```

> 키는 반드시 `agent/.env`에 넣는다. 루트 `.gitignore`에 `!.env.example` 예외가 있어 `.env.example`에 넣으면 커밋된다.

- 결과는 `agent/out/runs/`(git 무시)에 저장된다: 화면 조각 `screen.json`, 문서 `document.md`, 엔진 원본 `r1_도구.json`
- 질문 하나에 15~35초, Sonnet 호출 2~4회, 약 50~170원 (문서가 가장 길다)

## 3. 동작 구조

```
질문 (+ 시민 모드: 찾을 위치)
  │
  ├─ 시민 모드: 위치 없음·서비스 지역 밖 → Sonnet 을 부르지 않고 안내 문구
  ▼
Sonnet ──▶ 도구 호출 ──▶ 권한 확인 → 기준값 인자 제거 → (시민) 위치 채움 → 엔진 실행
  ▲                        → 결과 보관(r1, r2 …) → 요약을 Sonnet 에 전달
  └────────── 반복 ◀───────┘
  │
  ▼
제출: submit_answer (분석 답변) / submit_document (문서) / submit_brief (짧은 답)
  ──▶ 검증 ─┬─ 통과 → 화면 조각 (display + internal)
            ├─ 실패 → 고칠 점을 돌려주고 같은 도구로 다시 쓰게 함 (1회)
            └─ 또 실패·제출 없음·거절·API 오류 → 안내 문구 + 지도 (그릴 결과가 있을 때)
```

| 파일 | 하는 일 |
|---|---|
| `orchestrator.py` | Sonnet 도구 호출 반복. 질문당 Sonnet 최대 8회, 다시 쓰기 1회, effort `medium`, 시스템 프롬프트·도구 정의는 캐시 |
| `prompts.py` | 시스템 프롬프트 = 공통 규칙 + 관리자 규칙 / 시민 규칙. 엔진 숫자는 넣지 않는다 |
| `tools.py` | 엔진 도구 정의(`engine/tool_schemas.py`)를 불러와 모드별 도구 목록 구성, 제출 도구 정의 |
| `engine_client.py` | 엔진 호출. `LiveEngine`(실제 계산) / `FixtureEngine`(`engine/out/json` 예시, 테스트용) |
| `agent_tools.py` | 에이전트 쪽 도구: 시민 시간대, 시설 이름 검색, 어르신 생활 업종 (+ 아래 두 파일 등록) |
| `field_check.py` | 현장 확인 목록 (칸별 안정도) |
| `compare.py` | 세 개입안 비교 |
| `location.py` | 시민 위치 → 서비스 지역 판단 |
| `store.py` | 엔진 결과 전체 보관(r1, r2 …), `agent/out/runs/` 저장 |
| `digest.py` | 엔진 결과를 Sonnet 용으로 요약 |
| `verifier.py` | 답변·문서 검증, 신뢰도 등급 |
| `screen.py` | 화면 조각 생성 |
| `documents.py` | 문서 세 종류의 목차·분량 규격, Markdown 변환 |
| `terms.py` | 유형 쉬운 이름, 시민 금지어 |
| `run.py` | 터미널 실행 |

### 도구

| 도구 | 출처 | 관리자 | 시민 |
|---|---|---|---|
| 엔진 도구 8개 (`find_candidates` … `region_context`) | 엔진 공개 도구 | ✅ | `lookup_resources`만 |
| `find_facility` 시설 이름 → 시설 ID·주소 | 엔진 데이터 파일 읽기 | ✅ | |
| `field_check` 현장 확인 목록 | 엔진 내부 함수 `_universe` | ✅ | |
| `compare_interventions` 세 개입안 비교 | 엔진 공개 도구 3개 조합 | ✅ | |
| `senior_industries` 어르신 생활 업종 | 팀 EDA 결과표 읽기 | ✅ | |
| `senior_hours` 60대 이상 활동 시간대 | `region_context`에서 시간대만 | | ✅ |
| `submit_answer` / `submit_document` / `submit_brief` | 제출 (분석 답변 / 문서 / 짧은 답) | 셋 다 | 문서 제외 |

- 시민 모드에는 위험 판정이 나올 수 있는 도구를 **목록에서 빼고 실행 단계에서도 거절**한다. `region_context`도 결과에 유형별 칸 수가 있어 시민 모드에서 빼고, 시간대만 꺼내는 `senior_hours`를 대신 준다.
- `find_candidates`·`classify`의 기준값 인자(`persist_min`, `residential_filter`, `far_social_m`, `far_health_m`)는 도구 정의에서 빼고 실행 때도 버린다. 답변은 항상 엔진 기본값 기준이고, 기준을 바꾼 결과는 강건성 점검이 보여준다.

## 4. 답변을 믿을 수 있게 하는 장치

### 숫자는 엔진 결과에서만
- Sonnet 에는 엔진 원본 대신 요약을 넘긴다. 시나리오 도구 세 개 기준 약 15만 자 → 3천 자 (2%).
- 요약에서 인용할 수 있는 숫자는 `evidence`와 `params`뿐이다. 행정동 순위 같은 정보는 숫자 없이 이름·순서로만 넘긴다.
- Sonnet 은 화면 문장의 숫자마다 출처(`결과 번호` + `metric`)를 적고, 검증기가 엔진 값과 대조한다. 비율·차이·합 같은 계산값은 다시 계산해 맞춰 본다.

### 검증 규칙 (`verifier.py`)

| 검사 | 오류가 되는 경우 |
|---|---|
| 숫자 대조 | 출처 없는 숫자, 없는 출처, 값이 다름. `1,361`·`3km`·`%`·반올림은 같은 값으로 인정 |
| 이름 속 숫자 | 결과에 나온 행정동·시설·주소·시간대·업종 이름(예: 개포2동, 서부대성로 71, 12~17시) 속 숫자는 검사하지 않음 |
| 금지 표현 | 도구 이름, 결과 번호(`r2`), 칸 ID, 영문 지표 이름, `evidence`·`SGIS`·칸·위축 신호 등. 시민은 위험·고립·유형 표현도 금지 |
| 과정 수치 | 기준값(`params`)과 강건성 결과에서 온 숫자. 예외: 배치의 거점 수·반경, 시민의 반경, 제안서 '근거 데이터' 목차 |
| 필수 한계 | 질문에 쓴 도구에 따라 반드시 반영할 한계 문장 (예: 유동인구 ≠ 거주자, 접근성만 비교했음) |
| 숫자 표기 | 소수로 된 원래 비율 값(예: 0.5453), 같은 값을 괄호로 두 번 쓰기(예: 55%(0.5453)) |
| 분량 | 설명 300자 이상·문단 3개 이상, 문서는 목차별 분량·문자 90자 이내. 80자 넘는 문장은 경고만 |
| 도구 결과 없음 | 도구를 하나도 부르지 않은 분석 답변 (데이터 없이 일반 지식으로 지역을 판단하지 않게) |
| 짧은 답 | 숫자를 쓰거나 200자를 넘으면 오류 (분석 내용을 짧은 답으로 내보내 검증을 피하지 못하게). 분량·필수 한계는 보지 않음 |

> **검증 규칙을 고칠 때**: 위 규칙 중 이름 속 숫자·줄여 쓴 주소·거점 수 표기 같은 예외는 실제 실행에서 맞는 답이 막힐 때마다 하나씩 붙었다.
> 예외가 늘수록 서로 얽혀 다른 경우가 잘못 통과되거나 막힐 위험이 커진다. 검증 실패가 나오면 **규칙을 더하기 전에 프롬프트(`prompts.py`)로 답 쓰는 방식을 바꿀 수 있는지 먼저 본다.**
> 규칙을 고칠 때는 `agent/tests/test_verifier.py`에 막혀야 하는 답과 통과해야 하는 답을 함께 추가한다.

검증에 끝내 실패하면 **검증되지 않은 문장은 화면에 내보내지 않고** 안내 문구와 지도만 보여준다. 그릴 결과가 없으면 지도를 가리키는 문장을 뺀 안내 문구만 보여준다.

### 신뢰도 (관리자 화면만)
강건성 점검에서 기준을 하나씩 바꿔도 긴급방문형 판정이 70% 이상 겹치면 '높음', 아니면 '보통', 검증 실패면 '낮음'이다. 코드가 정하며 Sonnet 이 고르지 않는다. 지금 춘천·강남은 모두 '보통'이다.

### 사용자에게는 결론만
- 화면에는 결론과 설명만 쉬운 말로 보여주고, 분석 과정(도구, 지표 이름, 기준값, 계산 과정)은 내부 기록에만 둔다.
- "칸" 대신 "동네", 유형 이름에는 쉬운 이름을 붙인다 (예: 가장 먼저 방문이 필요한 동네(긴급방문형)). 시민 화면에는 유형 이름도 쓰지 않는다.
- 정보량은 줄이지 않고, 긴 문장은 여러 짧은 문장으로 나눈다.

## 5. 화면 조각 JSON

에이전트의 최종 결과다. **프론트는 `display`만 그리고, `internal`은 그리지 않는다.**

```json
{
  "mode": "admin | citizen", "question": "…", "region": "춘천",
  "display": {
    "headline": "결론 한두 문장",
    "details": ["문단1", "문단2", "…"],
    "caution": "확인할 점",
    "confidence": {"label": "보통", "note": "방문 전에 현장 확인을 권합니다."},
    "map": {"layer": "types", "ref": "r2", "geojson": null, "points": [ … ]},
    "chart": null,
    "document": null
  },
  "internal": {"verification": {…}, "confidence_basis": {…}, "citations": […], "caveats": […], "tool_trace": […], "run": {…}}
}
```

| 필드 | 내용 |
|---|---|
| `headline`, `details`, `caution` | 결론 / 문단 목록 / 확인할 점. 검증 실패 시 `headline`에 안내 문구, 나머지는 비어 있음. 짧은 답은 `headline`만 있고 지도·신뢰도는 `null` |
| `confidence` | 관리자만. 시민 화면은 `null` |
| `map` | 지도 레이어와 점 목록 (아래 표). 그릴 결과가 없으면 `null` |
| `chart` | 개입안 비교 질문일 때만: `{type: "bar", title, unit, total, items: [{label, value, remaining}]}` |
| `document` | 문서 요청일 때만: `{type, type_name, title, sections: [{heading, body}], markdown}` |

**지도 레이어** (점마다 `highlight`가 붙는다: 답변에서 언급한 곳)

| `layer` | 점 필드 | 언제 |
|---|---|---|
| `types` | `id, lat, lon, emd_name, type, gap` | 유형 분류 (낮 외출이 줄어든 동네 전체: 긴급방문형·연계형. 관찰형까지 전체 칸은 엔진 `types_*.geojson`) |
| `candidates` | `id, lat, lon, emd_name, months` | 후보 찾기 |
| `sites` | `id, lat, lon, emd_name, covers` | 이동형 거점 |
| `interventions` | `id, lat, lon, emd_name, option, name, facility_name` | 개입안 비교 (안별 거점) |
| `checks` | `id, lat, lon, emd_name, level, questions, order` | 현장 확인 목록 |
| `facilities` | `id, lat, lon, name, kind (, dist_m)` | 주변 시설, 시설 검색 |

- `id`는 칸 ID 또는 시설 ID다. 화면 글자로 보여주지 말고 상세 조회 키로만 쓴다.
- 강조 기준: 관리자는 결론 문장에 나온 행정동, 시민은 답변 전체에 나온 시설, 시설 변화 질문은 실제로 뺀 시설만.
- 시민 모드에서 Sonnet 을 부르지 않고 끝나는 경우(위치 없음, 서비스 지역 밖)는 `headline`에 안내 문구만 있고 `map`·`confidence`가 `null`이다.

## 6. 개발 과정

### 단계별로 만든 것과 주요 결정

| 단계 | 만든 것 | 주요 결정 |
|---|---|---|
| 엔진 연결 | `engine_client.py`, `store.py` | 엔진 공개 도구만 호출. 그림 도구는 `render=False`로 불러 git 이 추적하는 `engine/out` 을 덮어쓰지 않음. 예시 응답은 JSON 안의 `tool`·`params`로 골라 엔진 기본값을 코드에 적지 않음 |
| 요약 | `digest.py` | 인용 가능한 숫자는 evidence·params 만 (행정동별 칸 수 같은 result 숫자는 넘기지 않음). caveat 은 번호를 붙여 질문 하나에서 한 번만 원문으로 넘김 |
| 도구·권한 | `tools.py` | 기준값 인자 제거, 모드별 도구 목록 + 실행 단계 거절. 제출은 `strict` 도구로 받고 화면용 필드와 내부 기록을 나눔 |
| 검증 | `verifier.py` | 숫자 대조·금지 표현·과정 수치·필수 한계·분량. 신뢰도는 코드가 정함 |
| 화면 조각 | `screen.py` | `display`(프론트) / `internal`(로그) 분리. 검증 실패 시 문장 숨김 |
| 오케스트레이터 | `orchestrator.py`, `prompts.py` | 직접 짠 도구 호출 반복(도구 결과를 가로채 요약·보관해야 해서). 프롬프트는 공통 + 모드별 |
| 시민 모드 | `location.py`, `senior_hours` | 위치는 앱이 넘겨준 **찾을 위치**(가족이 대신 찾는 경우 포함). 지역 판단은 위치 → 칸 ID → 엔진 칸 확인, 칸이 없으면 옆 1칸까지. Sonnet 은 위치를 정하지 못하고 좌표도 받지 않음 |
| 관리자 질문 확장 | `find_facility`, 요약 보강 | 배치·시설 폐쇄·"믿어도 돼?" 지원. 강건성을 Sonnet 이 부르지 않으면 신뢰도용으로 코드가 부름 (짧은 답 제외) |
| 현장 확인 목록 | `field_check.py` | 기준을 엔진 기본값 ±20%(위축 개월 +1)로 바꾼 54조합에서 긴급방문형 유지 비율 계산. 80% 이상 안정(목록 제외), 50~80% 확인 필요, 50% 미만 꼭 확인. 흔들리는 기준별 확인 질문 |
| 개입안 비교 | `compare.py` | 경로당 거점 = 이동형 거점마다 가장 가까운 경로당(같은 수·같은 동네)에 보건 기능 추가 가정. 공통 지표 = 해소되는 긴급방문형 동네 수 |
| 문서 | `documents.py`, `submit_document` | 제안서·현황 보고·주민 안내문. 주민 안내문은 관리자 모드에서 만들지만 시민 금지어 적용, 모르는 정보는 `[날짜]` 같은 빈칸 |
| 카드 근거 | `senior_industries` | 카드는 시군구 단위라 가게 위치는 쓸 수 없음 → 어르신이 자주 쓰는 생활 업종을 안내문 둘 곳·함께 알릴 곳 제안에 사용 |
| 도시 성격 | `prompts.py`, `digest.py`, `verifier.py` | 엔진 지역 맥락의 로컬 결제 비율(`local_payment_pct`)로 방문 도시(강남) / 주민 생활권(춘천)을 밝히고 도움 방식이 왜 이 도시에 맞는지 설명 (엔진 10/3 caveat 기준). 이 값을 인용하면 '생활 반경·고립 신호로 해석하지 않는다' 한계가 필수. 주민 안내문·시민 모드에는 쓰지 않음 |
| 마무리 | `submit_brief`, 오류 처리 | 인사·관계없는 질문·지역 밖·데이터 없는 질문은 짧은 답. Sonnet API 오류·엔진 오류는 에이전트가 잡아 안내 문구 화면 조각으로 돌려줌 |

### 실제 실행으로 찾아 고친 문제

실제 Sonnet 으로 돌려 보면서 찾은 문제다. 대부분 **검증기가 맞는 정보를 막아 Sonnet 이 정보를 지우거나 바꾸던** 경우였다.

| 문제 | 수정 |
|---|---|
| "개포2동"의 2를 출처 없는 숫자로 잡자 Sonnet 이 "개포이동"으로 바꿔 통과 | 결과에 나온 이름 속 숫자는 검사하지 않음 |
| 줄여 쓴 주소("서부대성로 71"), "12~17시", "60대 이상"이 막혀 시민 답변에서 주소·시간이 빠짐 | 이름의 일부와 맞는 숫자, 시간대·연령 표기 인정 |
| 비율 0.5453 을 "54.5%"로, "3곳이면 73.1%"로 쓴 것이 막혀 거점 수별 커버 비율이 답에서 빠짐 | 비율 하나를 %로 쓴 값, 인용한 거점 수별 지표의 거점 수 인정 |
| 보건 기준 3km 와 이동형 반경 3km 가 한 문서에 나오자 기준값 위치 제한이 잘못 걸려 제안서 실패 | 같은 숫자를 허용된 출처로도 인용했으면 제한하지 않음 |
| 시민 모드에서 찾을 위치 좌표가 요약을 거쳐 Sonnet 에 넘어감 | 시민 모드 요약에서 좌표를 빼고, 모든 요청에 좌표가 없는지 테스트 |
| 자원 조회 요약에 시설 이름·주소가 없어 시설을 안내하지 못함 | 요약에 이름·주소 추가 |
| 칸 단위 우선 확인 목록이 행정동 순위와 기준이 달라 결론이 헷갈림 | 요약에서 칸 목록 제거 (위치는 지도가 보여줌) |
| 춘천(주택 기준)에 맞춘 프롬프트 예시를 강남(보건 거리)에도 그대로 써서 논리가 안 맞음 | 흔들리는 기준별 확인 문구로 일반화 |
| 문단 앞에 "어디, 왜:" 같은 제목을 붙임 | 프롬프트에서 금지 |
| 관리자 지도에서 50곳이 전부 강조됨 (설명에 행정동 순위 전체가 나와서) | 관리자는 결론 문장 기준으로 강조 |
| "약 55%(0.5453)"처럼 원래 값을 괄호로 덧붙임 (숫자는 맞아 검증은 통과했지만 어색하고 과정이 드러남) | 검증 규칙과 프롬프트에 추가 |
| "안녕" 같은 짧은 대화도 300자 규칙에 걸려 안내 문구로 끝나고, 관리자 모드에는 지역 밖 질문을 막는 단계가 없었음 | 짧은 답 제출 도구 추가, 도구 결과 없는 분석 답변 금지 |
| 제안서에 "동네를 중심으로 생활이 이뤄지는 도시"처럼 로컬 결제 비율을 생활 반경으로 바꿔 씀 (숫자는 맞아 검증은 통과) | 프롬프트에 "지역 가게를 누가 이용하는지"로만 말하라는 규칙과 금지 예 추가 |

### 최종 점검
- 테스트 170개 (API 키 없이, 가짜 Sonnet 과 예시 응답 엔진 사용), 엔진 테스트 18개 통과. `engine/` 코드는 수정하지 않았다.
- 마지막 코드 점검에서 짧은 답이 두 번 실패하면 멈추던 문제, 다시 쓰기 안내가 늘 `submit_answer`를 가리키던 문제, 도구 없이 제안서·보고를 쓸 수 있던 문제를 고쳤다.
- 백엔드 연결 전 점검: 백엔드처럼 `ask()`를 15가지 경우(전체 도구·시민·지역 밖·잘못된 인자)로 불러 모두 JSON 화면 조각이 나오는 것과 동시 요청을 확인했다. 지도가 없는데 "지도에 표시"라고 안내하던 문제, 점 0개 지도, 비어 있는 위치 값을 고쳤다. 짧은 답에는 신뢰도가 없으므로 신뢰도용 강건성 점검을 자동으로 부르지 않게 했다.
- 도시 성격 보강 후 실제 Sonnet·엔진으로 예시 6개(어디부터 춘천·강남, 이동형 배치, 개입안 비교 춘천·강남, 제안서)를 다시 만들었다. 모두 검증을 통과했고(제안서는 2회 제출), 도시 성격 문장과 한계 문장을 직접 읽어 확인했다.
- 관리자 11개·시민 2개 질문을 실제 Sonnet·엔진으로 실행해 모두 검증을 통과했고, 시민 안내 2개(위치 없음, 서비스 지역 밖)도 정상 동작했다. 결과는 [`out/examples/`](out/examples/)에 있다.

## 7. 팀원별 전달 사항

### 백엔드·프론트: 꼭 지킬 것과 바꿔도 되는 것

아래 채원·사랑 절의 코드와 처리 방식은 지금 에이전트에 맞춘 **예시**다. 개발하면서 더 나은 방식이 있으면 바꿔도 된다.
다만 다음은 바꾸면 에이전트가 잘못 동작하거나 설계 원칙이 깨지므로 지킨다.

| 꼭 지킬 것 | 이유 |
|---|---|
| `ask(질문, 위치)`로 부르고, 위치는 `{'lat', 'lon'}` | 에이전트 입력 형식이다. 바꾸려면 에이전트도 함께 고쳐야 한다 |
| `display`만 화면에 그리고 `internal`은 그리지 않는다 | 사용자에게는 결론만 보여주고 분석 과정·출처·검증 기록은 숨긴다 |
| 시민 화면에 위험·유형·신뢰도 정보를 따로 붙이지 않는다 | 시민 모드에서는 동네를 위험도로 나누지 않는다 (낙인 방지) |
| 지도 점의 `id`(칸 ID·시설 ID)는 화면 글자로 보여주지 않는다 | 내부 식별자다. 요청·조회 키로만 쓴다 |
| 시민의 찾을 위치를 저장하지 않는다 | 가족 집 주소일 수 있는 개인정보다 |
| 백엔드에 `config`·`core`·`render`·`tool_schemas`라는 최상위 모듈을 두지 않는다 | 엔진이 같은 이름을 써서 서버 시작 때 깨진다 (채원 절 참고) |
| 함께 가기·이동 도움 요청은 담당자가 확인한 뒤 연결한다 | 자동 매칭을 하지 않기로 정했다 (안전·책임) |

**팀원이 정해도 되는 것**
- 백엔드: 동기·비동기 처리, 시간 제한 값, 오류 응답 형식, 로그·요청 저장 방식, 함께 가기·이동 도움·현장 결과의 저장 구조와 처리 흐름
- 프론트: 화면 디자인과 배치, 문서를 `sections`로 그릴지 `markdown`으로 그릴지, 강조 표시 방식, 대기 표시, 지도 API, 체크리스트 화면, 버튼 위치

**화면 조각(JSON) 형식을 바꾸고 싶을 때**: 필드 추가·이름 변경·지도 점 필드 추가처럼 형식 자체를 바꾸려면 에이전트 쪽(혜진)에 알려 함께 고친다. 형식은 에이전트가 만들어 내기 때문이다. 받은 뒤 프론트·백엔드 안에서 변환해 쓰는 것은 자유다.

### 현준 (분석 엔진)

**에이전트가 의존하는 것** — 바뀌면 에이전트도 고쳐야 한다. 대부분은 테스트가 알려준다.

| 대상 | 내용 |
|---|---|
| 공개 도구 | `core.TOOLS` 의 도구 이름·인자, 응답 공통 형식, `engine/tool_schemas.py` 의 `SCHEMAS`(지역 목록 포함) |
| evidence 이름 | `n_긴급방문형` 등 유형 수, `*_gap_*`, `covered_senior_share_kN`, `covered_cells_kN`, `senior60_card_time_*`, `local_payment_pct`, `oat_*` 등. Sonnet 이 이 이름으로 인용한다 |
| result 필드 | 요약·지도에 쓰는 것: `classify`(`type_counts`, `layers`, `type_actions`, `by_emd_withdrawn`, `table`), `find_candidates`(`by_emd`, `cells`), `robustness`(`one_at_a_time`), `simulate_placement`(`chosen_sites`, `covered_cells`, `type_after`), `facility_change`(`removed`, `transitions`, `changed_cells`), `region_context`(`senior60_card_time_pct`, `lens`), `lookup_resources`(`nearest_by_kind`, `within_radius`) |
| `lookup_resources` | 다른 지역의 `cell_id`를 넣으면 `result.error`를 돌려주는 동작을 **시민 위치의 지역 판단**에 쓴다. 칸 ID = UTM-K(EPSG:5179) 좌표 ÷ 250 의 몫이라는 규칙도 쓴다 |
| caveat 문구 | 필수 한계 판정에 문장 속 구절을 쓴다: "거주자와 같지 않다", "두 층", "공공 보건기관", "고립 감소 효과를 뜻하지 않는다", "직선거리", "세부 프로그램은 기관 확인", "생활 반경·고립 신호로 해석하지 않고" |
| 예외 3가지 | ① `field_check`가 `core._universe`와 `config`(교류·보건 거리, 위축 개월, 주택 기준 기본값)를 씀 ② `find_facility`·`compare`가 `preprocessed/facility.parquet`(`fac_id, region, group, kind, name, addr, lat, lon`)을 읽음 ③ `senior_industries`가 `outputs/tables/18·19·23·24` 표를 읽음 |

**선택 개선** — 에이전트는 지금 엔진 그대로 모든 기능이 동작한다. 아래는 여유가 있으면 좋아지는 것이다 (우선순위 순).

| 순위 | 개선 | 없을 때 보이는 영향 |
|---|---|---|
| 1 | 원천 시설명 다듬기 | 강남구 경로당 원천 데이터의 시설명이 "도곡", "미성2차㉵"처럼 장소명만 있고 `㉵`(아파트 약칭으로 보임)가 붙어 있다. 관리자 답변은 행정동 이름으로 피했지만, 강남 시민 모드에서 경로당을 안내하면 이 이름이 그대로 보일 수 있다 |
| 2 | 칸별 유형 전체 목록 | ✅ 10/12 반영. `classify.table`이 위축 칸 전체(춘천 153·강남 51)를 담아 유형 지도에 빠지는 동네가 없다 |
| 3 | 자원 조회 evidence 에 시설별 거리 | 종류별 가장 가까운 시설의 거리만 있어, 시민 답변에서 두 번째로 가까운 시설부터는 거리를 말하지 못한다 (지도 점에는 거리가 있다) |
| 4 | 시설 이름 검색 공개 도구 | 화면 영향은 없다. 지금은 에이전트가 시설 데이터 파일을 직접 읽어서, 파일 열 이름이 바뀌면 에이전트를 고쳐야 한다 |

### 채원 (백엔드)

**1. 에이전트 연결**

```python
from agent.engine_client import LiveEngine
from agent.orchestrator import Orchestrator

engine = LiveEngine()                                   # 서버 프로세스에 하나
admin = Orchestrator(engine, mode='admin')              # 모드별로 하나씩 만들어 재사용
citizen = Orchestrator(engine, mode='citizen')

screen, turn = admin.ask('춘천에서 어디부터 확인해야 해?')
screen, turn = citizen.ask('근처에 갈 만한 곳 있어요?', location={'lat': 37.8813, 'lon': 127.7298})
```

- 입력: 모드, 질문, 시민 모드는 찾을 위치 `{'lat', 'lon'}` (프론트가 정해서 보냄). 위치가 없거나 값이 비어 있으면 위치를 고르라는 안내가 돌아온다
- 출력: `screen['display']`는 프론트로 보내고, `screen['internal']`은 로그로만 저장한다
- 저장소 루트를 import 경로에 두고, API 키는 `agent/.env`의 `ANTHROPIC_API_KEY`에 둔다
- `save_run()`·`python -m agent.run`은 **개발 확인용**이다. 모든 요청이 같은 폴더(`agent/out/runs/`)를 지우고 다시 써서 서버에서 쓰면 요청끼리 결과가 섞인다. 서버에서는 `screen['internal']`을 요청별로 저장한다

> **모듈 이름 주의**: 엔진은 `config`, `core`, `render`, `tool_schemas`를 최상위 모듈 이름으로 쓴다 (`import config`).
> 백엔드에 같은 이름의 모듈(예: FastAPI 프로젝트의 `config.py`)이 있으면 엔진이 그 모듈을 잘못 불러
> 서버 시작 때 `LiveEngine()`에서 `module 'config' has no attribute 'PERSIST_MIN'` 같은 오류가 난다.
> 백엔드 모듈은 패키지 안에 두거나(`app/config.py` → `from app import config`) 다른 이름을 쓴다.

**2. 응답 시간과 오류**
- 질문 하나에 15~35초(문서는 1분 안팎) 걸리고 답은 한 번에 온다. 요청 시간 제한을 넉넉히 두거나 비동기(요청 접수 후 결과 조회)로 처리한다.
- Sonnet API 오류와 엔진 오류는 에이전트가 잡아서 안내 문구가 담긴 화면 조각으로 돌려준다. 백엔드는 그 밖의 예상 못 한 오류와 시간 초과만 `ask()` 바깥에서 감싸 공통 오류 응답을 주면 된다.
- Sonnet 호출 하나의 시간 제한은 SDK 기본값(10분, 실패 시 2번 재시도)이라 질문 하나가 아주 오래 걸릴 수 있다. 응답 시간을 묶으려면 시간 제한을 정한 클라이언트를 넘긴다. 시간 초과는 API 오류로 잡혀 안내 문구 화면 조각(`internal.run.end == 'api_error'`)이 된다.

```python
import anthropic
from dotenv import load_dotenv
from agent.orchestrator import ENV_FILE
load_dotenv(ENV_FILE)                                       # agent/.env 의 API 키
client = anthropic.Anthropic(timeout=60, max_retries=1)   # Sonnet 호출 1회당 60초, 재시도 1번
admin = Orchestrator(engine, mode='admin', client=client)
```
  질문 하나에 Sonnet 을 2~4번(최대 8번) 부르므로, 전체 요청 시간 제한은 이보다 넉넉히 둔다.

**3. 백엔드가 만들 기능**

| 기능 | 받는 정보 | 처리 |
|---|---|---|
| 함께 갈 이웃 찾기·이동 도움 요청 | 시설 `id`(`display.map.points`), 요청한 사람, 실제로 가는 사람, 희망 날짜 | 가족이 대신 요청할 수 있어 요청자와 가는 사람을 나눠 받는다. 담당자가 확인한 뒤 연결한다 (자동 매칭 아님) |
| 현장 확인 결과 저장·판정 덮어쓰기 | 칸 `id`(`checks` 레이어 점), 확인 질문별 답 | [`현장기록_규격.md`](../engine/현장기록_규격.md)대로 저장하고 두 가지 답만 판정에 반영한다 (사람이 사는 집 없음 → 제외, 지원 불필요 → 관찰형). 에이전트·엔진은 바꾸지 않으므로 에이전트 답변 속 숫자에는 반영되지 않는다 |

**4. 지켜야 할 것**
- 시민의 찾을 위치(가족 집 주소일 수 있음)는 저장하지 않는다.

### 사랑 (프론트)

**1. `display`만 그린다**

| 필드 | 화면 요소 | 비고 |
|---|---|---|
| `headline` | 결론 | 짧은 답·안내 문구일 때는 이것만 있다 |
| `details` | 설명 문단 목록 | 문단 안의 `- ` 목록 줄은 줄바꿈을 살린다 |
| `caution` | 확인할 점 | 비어 있으면 숨긴다 |
| `confidence` | 신뢰도 (`label` + `note`) | 관리자 분석 답변만. 그 밖에는 `null` |
| `map` | 지도 | 레이어별 점 필드는 5절 표. `null`이면 지도 없음 |
| `chart` | 막대그래프 | 개입안 비교 질문만 |
| `document` | 문서 화면 | 문서 요청만. `sections`로 그리거나 `markdown`을 보여주고 복사·내려받기 |

**2. 지도**
- 점은 `lat`·`lon`으로 찍고, `highlight: true`인 점(답변에서 언급한 곳)은 강조한다.
- `types` 레이어는 `type`(긴급방문형·연계형)으로 색을 나눈다.
- `id`는 화면에 보여주지 않고 요청·조회 키로만 쓴다.
- 현장 인력 체크리스트는 `checks` 레이어 점으로 그린다: `order` 순서로 방문 목록, `level`(꼭 확인/확인 필요), `questions` 체크 항목.
  저장 키(`has_residents` 등)와 질문 문구의 대응, 모든 동네에 고정으로 묻는 `support_needed`는 [`현장기록_규격.md`](../engine/현장기록_규격.md) 3절을 따른다.
- 전체 칸 지도(관찰형 포함)·시설 지도 파일은 [`지도_규격.md`](../engine/지도_규격.md)를 따른다. 응답 지도 점의 `gap`·`months`는 엔진 지도 파일의 `gap_tag`·`persistent_months`와 같은 값이다.

**3. 시민 모드**
- 찾을 위치를 앱이 정해 백엔드로 보낸다: 위치 허용(GPS), 지도에서 동네 고르기, 주소 입력 중 하나. 주소 → 좌표 변환은 지도 API 로 한다.
- 시설 카드마다 길찾기·함께 갈 이웃 찾기·이동 도움 요청 버튼을 둔다. 필요한 정보(시설 `id`·이름·위치·거리 `dist_m`)는 `map.points`에 있다.

**4. 대기 표시**
- 답이 오는 데 15~35초(문서는 1분 안팎) 걸려 진행 중 표시가 필요하다.

실제 화면 조각 예시: `out/examples/5_관리자/*/화면조각.json`, `6_시민/*/화면조각.json`
